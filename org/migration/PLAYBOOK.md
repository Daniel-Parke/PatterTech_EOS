# MIGRATION PLAYBOOK

How one venture moves from a v1 seed to a v2 seed. Deterministic,
read-only until the operator says otherwise, and never run on a
schedule.

## The consent rule

A venture moves when its operator chooses and at no other moment. Pins
are the isolation mechanism: a venture records the EOS commit it
compiled from and reads nothing from this repo at runtime, so releasing
v2 changes nothing in any venture until someone recompiles. There is no
auto-upgrade, no deprecation clock and no push. A venture that never
migrates keeps working under the kernel it was born with, and its seed
check still judges it by the matrix at its own pin.

## Step 1 · Plan, read-only

From the EOS repo:

`python -m tools.eos migrate plan --seed <venture path>`

The command writes nothing. It reads the venture's lock-book header for
scale and pin, inventories the seed against the v1 scale matrix,
proposes a route, and prints a migration-state document valid under
kernel/schemas/migration-state.schema.json. The steps it lists are the
transforms the route implies, each still pending.

Read the inventory line. "inventory complete" means every file the v1
matrix required at that scale is present. Anything else names the
missing files, and a seed with holes gets them explained before it
migrates.

## Step 2 · Choose the route

Three routes exist. The plan proposes one; the operator confirms it.

**recompile.** The venture's pin predates the kernel freeze, so its
seed was compiled from templates that no longer describe the system.
Session 0 runs again from the ruled lock-book: the rulings, the brief
and the risk surface are inputs the venture already holds, so the
interview is a confirmation pass rather than a fresh one, and phases C
to E run in full against the v2 matrix.

**apply.** The venture's pin is a released v1 kernel and its seed
matches that matrix. The transforms are mechanical, so
`python -m tools.eos migrate apply` performs them and the lock-book
gains the v2 policy pin without a fresh walk.

**fresh-inception.** No lock-book exists, so the venture was never
compiled from the EOS. It runs Session 0 from the start per
inception/INCEPTION.md, or Express if its risk triggers are silent.

The route heuristic reads the lock-book's eos_version. A version
beginning with a zero, or one the reader cannot parse as a bare semver,
routes to recompile; a bare one-point-something routes to apply; a
missing lock-book routes to fresh inception. A pin written with a
leading v therefore falls to recompile, which is the stricter of the
two and safe. It also means the venture has a pin-normalisation job to
do: a pin must resolve to a pushed tag or a commit reachable from
origin, and check S010 enforces that in registry/PROJECTS.md.

## Step 3 · What is preserved, verbatim

The migration never rewrites the venture's own history or judgement.
Carried across untouched:

- The lock-book rulings, with their argued or inherited marks and their
  notes. A v1 ruling is an argument of record and stays one.
- Every ADR in the venture's decisions directory.
- Every session log the venture wrote.
- The feedback file, including anything the harvest has not yet read.
- The venture brief, apart from facts the operator corrects in the
  confirmation pass.
- Any product, design or compliance material the venture authored
  itself. The compile marks it preserved in the report rather than
  touching it.

## Step 4 · What changes

- The lock-book header gains the v2 pins: policy_profile,
  packs_adopted, and a scale of S or ORG where it read S, M or L.
- Role charters swap for the tier policy note, because charters are now
  adopted per task rather than held per session.
- Queue rows become task records under org/tasks/, one JSON file each,
  and the derived views are regenerated by the integrator.
- The worklog gains a migration note and stops being the work surface.
- A policy file appears, compiled from the template and filled from the
  venture's risk surface, with guard validated false until a bypass
  suite report exists.

## Step 5 · The validation gate

`python -m tools.eos check --seed <venture path>` must come back with
zero errors before the migration is called done. Then the operator
signs the human rubric items again, headed by the cold-start test,
because a migrated seed is a new seed and the only proof it works is a
cold session finishing a task from it. The compile report gains a fresh
sign-off block and the old one stays above it.

Finally the venture's row in registry/PROJECTS.md is updated: the new
pin, the scale as recompiled, the packs adopted, and the verification
date.

## What this build may not do

ADR-0002 reserves every write to a sibling venture repository for a
later decision. In this build the migration engine is exercised on
fixture seed copies only: `migrate apply` refuses outright to run
against a git repository, and the command refuses a seed path outside
this repo. The per-venture files under org/migration/plans/ are
read-only plan reports, produced by running step 1 and recording what
it actually said.
