# Restore drill and its evidence record

Level-3 reference for binding requirement 5 in
`packs/devops-reliability/PACK.md` and for the ruling in
`packs/devops-reliability/guides/WG-OPS-003-restore-proof.md`.

## Before the drill: the objectives and the hypothesis

Two numbers are written down before any drill runs, and they are the
operator's numbers, not the platform's defaults:

- **RTO**, the recovery time objective: how long the venture can be down
  before the damage is unacceptable.
- **RPO**, the recovery point objective: how much recent data the
  venture can afford to lose.

Then the steady-state hypothesis, stated before anything is touched
(EV-0203). It names the observable output that should hold after the
restore, in terms a query can settle. For example: after restoring the
most recent snapshot into a fresh instance, the contacts table holds
every email address present at the capture point, with the same row
count and the same value set. A drill without a hypothesis produces a
story; a drill with one either falsifies it or does not.

## The procedure

1. Capture the pre-drill state with the validation query against the
   live source, and store the result.
2. Restore the most recent backup into a fresh location. Never restore
   over the source, and never restore into an environment anything else
   is reading.
3. Run the validation query against the restored data. Querying the data
   back out is the step the anti-pattern list exists to force
   (EV-0201).
4. Compare row counts and value sets against the capture.
5. Record elapsed wall-clock time from start to a validated restore, and
   the age of the restored data against the capture point.
6. Compare elapsed against RTO and data age against RPO. Missing either
   raises an alert and files work; it does not quietly pass.
7. Tear down the restored location.

The script is committed and re-runnable. A drill whose evidence cannot
be regenerated by running the committed script is an assertion, not
evidence.

## The evidence record

One JSON document per run, written to the venture's evidence directory.
The key set is fixed so a checker can read it without knowing the
venture:

```json
{
  "started_at": "2026-08-03T02:00:00Z",
  "completed_at": "2026-08-03T02:11:42Z",
  "elapsed_seconds": 702,
  "rto_seconds": 3600,
  "rpo_seconds": 86400,
  "rows_validated": 4128,
  "validation_query": "select count(*), md5(string_agg(email, ',' order by email)) from contacts",
  "result": "pass",
  "hypothesis": "every email present at capture reads back through contacts, same count and same value set",
  "notes": "restored into a scratch instance, torn down at 02:14Z"
}
```

`result` is `pass` only when the validation query matched the capture,
`elapsed_seconds` is at most `rto_seconds`, and `rows_validated` is
greater than zero. Anything else is `fail`, and a failed drill is a
successful experiment: it found the thing before the outage did.

## What this does not cover

EV-0201 says nothing about restore under adversarial conditions, so
ransomware, credential loss and a compromised backup store are outside
this procedure and need their own treatment in the security-privacy
pack. The implementation guidance in that source is tied to specific
managed services; the principle is portable, the automation is not.

## Cadence

Monthly from the first production deploy is the estate starting point.
Regulated or attestation-grade data links the evidence record from the
compliance registry row that demands it. Raise the cadence after any
drill that failed, until two consecutive runs pass.
