# EX-SUPPLY-001: the first published release

One venture, one release, the pack loaded and nothing else. A small
Python command-line tool that people will install from a public
registry. Its build downloads a prebuilt binary from a third party,
because the tool shells out to it. Nothing about the task mentions
supply chain.

## Step 1: activation

Path triggers fire on three counts: the lock file, the release workflow
under the workflow directory, and a fetch script under the build. The
task type is "cutting a release".

Predicates: `publishes_code` and `ships_a_binary` are true from the
venture's interview answers. `builds_release_artefact` is true of this
task. `consumes_prebuilt_artefact` is true because of the downloaded
binary. `vendors_code` is false, and the run says so rather than
inventing a vendoring story.

Routing: publishing to a registry is boundary contact and is a guarded
class, so the publish itself will need a recorded operator approval
under the security pack. This pack sets no tier of its own.

## Step 2: the prebuilt binary nobody had looked at

The build fetches a release archive from a third party by URL, with no
digest. It has worked for months.

B1 applies. The fix is small and the reasoning is worth writing down:
the URL names a release, the release page can be edited by whoever owns
it, and nothing in the tree records which bytes were expected. The
change pins the archive by SHA-256, records where that digest came
from, and makes the fetch fail if it does not match.

The run also checks whether the third party publishes a signature.
They do not. That is recorded as a fact about the dependency rather
than as a failure of this release, and it goes in the lock-book beside
the pin so the next person does not have to look it up. Reading the
repository rather than its own description (EV-0069) turns up a second
fact worth recording: releases there are cut by hand from a laptop, so
there is no build to attest to even in principle.

## Step 3: provenance for what we publish

Under GD-SUPPLY-001 the ecosystem has a mechanism, so option B applies:
the registry accepts attestations generated by the hosted build. The
release workflow generates one, binding the distribution digest to the
source revision.

Under GD-SUPPLY-002 the identity is short-lived rather than a key
anybody holds (EV-0068). No long-lived key is created as a fallback,
because a fallback key would be a second path with the same authority
and less scrutiny.

The release notes then say one sentence, and the wording is the whole
point: this release was built by the project's own workflow from the
tagged revision, and the attestation is there to check. They do not say
verified, and they do not say secure. The mechanisms' own documentation
says provenance proves where an artefact was built and not what is in
it, and repeating that narrow claim costs nothing.

## Step 4: the publish path

B4 applies, and this is where the release nearly went wrong. The
existing workflow ran the tests, built the artefact and published, all
in one job, triggered on every push including from forks, with a
repository-wide token.

The change splits it. Building and testing stay on the ordinary
trigger. Publishing moves to a separate workflow triggered only by a
tag, with the publish scope granted to that job alone and the default
token read-only everywhere else. The third-party steps in both
workflows are pinned to commit digests rather than tags.

The reasoning is in `packs/supply-chain-integrity/refs/build-system-reach.md`:
a compromised build that can sign produces a real signature on a bad
artefact, and no downstream check catches that.

## Step 5: admission, in the direction people forget

The venture verifies what it publishes. It was verifying nothing of
what it consumes.

B3 applies. The fetch step now compares the downloaded digest against
the pin and stops the build on a mismatch or on an absent file. The run
tests the check by feeding it a wrong digest once and confirming the
build fails, because a verification step that has never failed is a
step nobody knows works. That is the difference between C7 and a hope.

The four steps in
`packs/supply-chain-integrity/refs/admission-checklist.md` are followed
in order. Step four, checking the identity behind the claim, does not
apply here: there is no claim, only a digest, and the run records that
gap rather than describing a control it did not build.

## Step 6: the bill of materials

Generated from the lock file, not by scanning the built wheel, which is
what the measurement behind the pack supports. It records that the
downloaded third-party binary is present and that its contents are not
enumerated, because nothing here can enumerate them.

That incompleteness note is the useful part of the document. Without
it, a reader takes the absence of entries for that binary as evidence
there is nothing in it.

## Step 7: cadence

Under GD-SUPPLY-003 the venture takes the default: a cooldown window on
third-party dependencies, its own internal packages exempted by name,
security fixes exempt from the window. The exemption is written down as
a deliberate hole rather than left as a setting nobody chose, because a
malicious release published as a security fix goes straight through it.

## What made this work

Four cheap rules, none of which required anybody to be clever about
security. What we consume is named by its bytes. What we publish can be
traced back to a build. Something checks, and stops when the check
fails. The thing that can sign is not the thing that reads untrusted
input.

The one thing the venture did not buy is any claim that the tool is
safe. It bought the ability for a stranger to establish where it came
from, and the ability for itself to notice if a dependency changed
underneath it. Verification at admission is against a stated
expectation rather than trust in the producing workflow (EV-0038), and
that expectation is now written down where the next release can find
it.
